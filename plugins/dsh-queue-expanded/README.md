# 排队消息默认展开

运行中的会话点击输入框的普通发送按钮时，使用 DSH 公开的 `inputActions.submit()` 排队入口。它固定采用 `queue`，不再借用原生按钮可能选择的 `steer` 模式；主任务结束前只在原生待发送列表中显示，结束后由原生队列按顺序执行。准备交接期间的 `awaitingFirstTurn` 和尚未退场的提交也纳入保护。

仍由原生输入状态机负责草稿、引用、附件、上传、接收回执、失败恢复和重复提交。只接管有实际内容、可提交的普通主按钮点击；空输入时的停止、模型选择、禁用或发送中的按钮、斜杠命令不接管。键盘快捷键、队列逐条插话发送、编辑、删除继续使用原生行为。当前通用设置保持“排队发送”，因此普通 Enter 同样排队；Cmd/Ctrl+Enter 保持显式插话操作。

队列有多条消息时自动展开，保留原生编辑、删除和插话操作。插件通过 `conversation.input.overlay` 管理发送保护的生命周期，返回隐藏挂载点，不增加可见控件。会话切换或停用后移除事件监听；不新建第二份队列，不直接清空草稿或移动 React 管理的消息节点。

## 回归约束

- 主按钮的 busy 标记也可能被其他组件使用；必须排除带 `aria-haspopup` 的模型选择器，避免选择模型误触发发送。
- 判断提交是否可用时保留原生 disabled、输入阶段、上传和命令边界。不要用 DOM 中的“进行中”文案推断真实运行状态。
- 排队成功必须有真实 Inbox `next-turn` 证据；列表可见不等于已正确延后执行。原生 `next-step` 代表插话，不能把它伪装成待发送行。
- 正常发送与模型、停止、队列编辑按钮必须分开验收；不能将整个输入卡片的点击都改成发送。

## 实际验收（1.1.0）

复用当前桌面 Host，以无头客户端验证：运行中点击、普通 Enter、多条队列自动展开、同一按钮连续触发不重复、任务完成后按顺序执行、未发送草稿保留、队列编辑保存和删除、带文件消息排队及移除、打开模型选择不发送草稿、停止当前任务、停止后正常发送。页面脚本错误为零。

额外把原生模式暂时改为“插话发送”，验证普通按钮仍将两条消息送入 `next-turn`。真实 Session Log 中两条消息在 seq 17/18 入队，主任务 seq 28 结束后，seq 29/36 才分别开始执行后续轮次；没有在原任务中被提前处理。验收后设置恢复为原来的“排队发送”。初始默认排队设置下普通运行未复现提前发送；本次新增明确排队入口，避免普通点击依赖原生模式选择。


## 失败、中断与队列持久化验收（2026-11-18）

本轮没有改动队列代码，验证使用当前 1.1.0。手动停止在现有桌面 Host 与真实模型上验证；模型失败使用隔离的已安装 Host 和本地受控 HTTP 400 响应；异常中断则在同一隔离 Host 持有模型请求和两条排队消息时强制结束进程，再启动并重新打开原会话。

三种场景均确认：原任务分别记录为 `aborted`、`error`、`interrupted`；两条消息继续留在 `next-turn`，未提前提交，刷新或进程恢复后仍保留。主动恢复后，六条排队消息各只出现一次真实 `user/message`，入队时与执行时的消息 ID 相同，A/B 顺序不变。受控失败和崩溃恢复的模型请求记录也确认每条消息只调用一次。停止、失败场景还核对了同一浏览器来源下的未发送草稿保留；进程重启测试改变了端口，仅以 Host 持久队列作为验收对象。

以后不要在失败、停止或断线时清空原生队列，也不要在组件挂载、刷新或重连时把列表内容再提交一遍。已接收的消息由原生 Inbox 持久化；界面恢复只读取投影。尚未被 Host 接收的提交则仍由原生输入状态机处理，不把乐观显示当成持久化成功。


## 多对话并行与切换验收（2026-11-18）

在原有桌面 Host 中创建两个测试对话，两个主任务同时运行约 83 秒，各排队两条消息，其中各有一个独立文件附件。运行期间完成 16 次交替切换；覆盖点击与 Enter、提交后立即切走、各自草稿、编辑 A 的队列后查看 B、排队时刷新。两边自然完成并清空队列后，再刷新和切换核对。

真实 Session Log 确认四条消息均只进入所属对话的 `next-turn`，每条仅有一次正式 `user/message`，与入队 ID 一致，且都在各自主任务结束后按顺序执行。两边附件 ID 不同且文件名称归属正确，未发现串话、丢失或重复。队列与草稿在多次切换和刷新期间保持各自状态；本轮仅验证并补充约束，未修改队列代码。

后续保持会话作用域：提交动作与输入状态必须来自同一 Session 绑定，不能把当前选中对话、全局草稿或全局待发送数组作为异步回调的归属来源。事件监听随所属挂载点卸载，切换后不能沿用上个会话的提交动作；队列编辑、附件和接收回执都按各自 Session 身份处理。
